OpenCode SDK v2: Impact Analysis for ai-sdk-provider-opencode-sdk

Date: 2026-08-26 Provider version analyzed: 4.1.0 (AI SDK v7 / LanguageModelV4, @opencode-ai/sdk ^1.18.11 via its /v2 entrypoint) v2 evidence base: @opencode-ai/client@0.0.0-beta-18286 and @opencode-ai/sdk@0.0.0-beta-18286 (published 2026-08-26), their full .d.ts surfaces, and the v2 docs at opencode.ai/v2/docs/build (build, sdk, client, plugins pages). Method: Four independent analyses — Claude Fable 5, GPT-5.6-Sol (max reasoning, via Codex), Grok 4.6 (high), and Kimi K3 (max, via pi) — each working read-only from the same ground-truth type definitions, docs snapshots, and provider source; converged by Claude, then iterated through 8 adversarial validation rounds by GPT-5.6-Sol against the beta .d.ts ground truth (25 blocking findings raised, independently verified, and incorporated) until validator sign-off with zero open issues. All four analyses independently reached the same top-level conclusions.

Executive summary

OpenCode v2 is a new backend, not an SDK bump. Every layer this provider touches changes simultaneously:

Layer v1 (current) v2 (beta)
Package @opencode-ai/sdk/v2 → createOpencodeClient @opencode-ai/client → OpenCode.make({baseUrl, headers?, fetch?}); @opencode-ai/sdk is now an embedded in-process host (Effect-based)
Results {data, error} fields-style Payloads returned directly; typed errors thrown (_tag unions + ClientError)
Prompt Blocking session.prompt({parts, model, system, tools, format, …}) → {info, parts} Fire-and-forget session.prompt({sessionID, text, files?, delivery?, resume?}) → inbox receipt; model/agent are session state
Streaming message.part.updated snapshots + prefix-diffing Native delta events (session.text.delta, session.reasoning.delta, session.tool.input.delta) + execution lifecycle events
Questions question.asked / question.reply(answers: string[][]) Forms: form.* API with typed, keyed fields
Permissions permission.reply({requestID, …}); per-session ruleset at create permission.reply({sessionID, requestID, …}); rules live on agents/config, not session create
Structured output format: json_schema + StructuredOutput tool Gone — no schema-enforced output anywhere in the beta prompt path
Server lifecycle createOpencodeServer({hostname, port}) + health probes Service.discover/ensure/stop/headers (registration file, version predicate, basic auth) or embedded OpenCode.create()

Recommendation (unanimous across all four analyses): clean-break v5.0.0 targeting @opencode-ai/client, with 4.x maintained for OpenCode 1.18 servers. Develop against the beta now under a next dist-tag with an exact version pin; do not GA until OpenCode v2 stabilizes. Add an optional ./embedded entrypoint for the in-process host (kept out of the default dependency graph — it hard-depends on effect@4.0.0-rc). The four hardest gaps — structured output, per-prompt system prompt, file-attachment ingestion, and inbox→execution correlation — should be raised upstream now, while v2 is still beta.

1. V2 change inventory

Everything below is verified against the beta .d.ts files (cited by type/method name); items marked (docs) come from the v2 docs prose.

1.1 Packaging and runtime topology

  • Package split. v2 @opencode-ai/sdk is an embedded in-process host (OpenCode.create(); deps: @opencode-ai/{client,core,plugin,schema,server,util} + hard effect@4.0.0-rc.111). The network client is @opencode-ai/client — exports ././promise (browser-compatible Promise client), ./service (Node-only process management), ./solid, ./effect* (Effect and solid-js are optional peers; the Promise root is Effect-free). There is no /v2 subpath in either package — the provider's @opencode-ai/sdk/v2 import sites (four in production source, plus exported types derived from them) have no drop-in replacement.
  • Embedded host ownership. OpenCode.create() returns Omit<OpenCodeClient, "plugin"> & {sessions, events, plugin, close, [Symbol.asyncDispose]} — the same Promise values, typed errors, and AsyncIterable events as the network client, with no HTTP listener. A ./workerd entry boots the host inside a Cloudflare Durable Object (SQLite on DO storage).
  • No engines field in either beta manifest; docs use bun add …@beta / …@dev (note: different dist-tags per package). The provider's Node >=22 floor should be retained as its own stability floor.
  • Repo moved to anomalyco/opencode.

1.2 Client construction, results, errors

  • OpenCode.make({baseUrl, fetch?, headers?}); each operation takes trailing RequestOptions {signal?, headers?}. Gone from client config: directory, responseStyle, throwOnError, interceptors, serializers, SSE retry knobs, experimental_workspaceID.
  • Methods resolve directly to payloads and throw on failure: tagged errors with _tag discriminants and exported guards (UnauthorizedError, ForbiddenError, InvalidRequestError {kind?, field?}, SessionNotFoundError {sessionID}, SessionBusyError {sessionID}, ProviderNotFoundError, AgentNotFoundError, MessageNotFoundError, ConflictError, ServiceUnavailableError, FormNotFoundError, FormAlreadySettledError, FormInvalidAnswerError, PermissionNotFoundError, UnknownError, …; guards named isUnauthorizedError, isSessionBusyError, etc.) plus transport-level ClientError {reason: "Transport"|"UnexpectedStatus"|"UnsupportedContentType"|"MalformedResponse"|"SseEventTooLarge"}.
  • Headers are the auth story — global at make(), per-request override in RequestOptions. This finally gives a direct mapping for AI SDK LanguageModelV4CallOptions.headers, which the provider currently ignores. Locally managed services may require basic auth (Endpoint.auth), constructed via Service.headers(endpoint) — a raw fetch(baseUrl + "/health") probe would 401.
  • The generated Promise client does not expose response headers or raw Response objects; AI SDK response-header metadata cannot be populated without a custom-fetch side channel.

1.3 The prompt contract (largest behavioral break)

SessionPromptInput: {sessionID, text (required), files?: [{uri, name?, description?, mention?}], agents?, skills?, id?, metadata?, delivery?: "steer"|"queue", resume?} → returns SessionInboxUser {id, sessionID, timeCreated, type: "user", payload, delivery} — an inbox receipt, not the assistant response.

Removed from the prompt (all present in v1): parts[], model, agent, system, tools, format (json_schema), variant, noReply, messageID (now id), directory. Consequences:

  • Model/agent are session state: set at session.create({title?, agent?, model?: {id, providerID, variant?}, location?}) or via session.switchModel/switchAgent (note the rename: v1 modelID → v2 ModelRef.id; v1 variant folds into the model ref). Two concurrent AI SDK calls with different models against one session now race server-side state.
  • Completion is observed, not returned: session.wait({sessionID}) → Promise<void>, execution lifecycle events (session.execution.started/succeeded/failed/interrupted), session.idle; the assistant message is fetched via message.list, session.message, or session.context, or assembled from delta events.
  • Busy/delivery semantics exist but are under-specified. The types prove that delivery: "steer" | "queue", resume, SessionBusyError {sessionID}, and SessionExecutionInterrupted.reason: "user"|"shutdown"|"superseded" all exist; they do not establish the default delivery, exactly when a busy session throws vs. enqueues, whether steer auto-interrupts (plausibly producing reason: "superseded"), or what resume continues. Treat these as behaviors to verify against a live beta (§5) before the provider relies on them.
  • Files are URI-only at the input boundary ({uri, name?, …} — no mime, no bytes). The stored PromptFileAttachment has {data: PromptBase64, mime, source: inline|uri}, implying base64 normalization happens server-side, but whether data:/file: URIs are accepted inbound is not type-evident. The provider's entire base64-data-URL attachment path is at risk.
  • New structural inputs with no AI SDK analog: agent/skill mentions with {start, end, text} ranges.

1.4 Session lifecycle and location

  • session.abort → session.interrupt({sessionID, continue?}) → {interrupted: boolean}.
  • Location model: client-level directory is gone; LocationRef = {directory, workspaceID?} binds at session.create({location}) and can change via session.move. Catalog/list APIs take location?: {directory?, workspace?}; session-scoped calls take only {sessionID, …}.
  • SessionCreateInput has no permission field (v1 had one) and no metadata/parentID; forking is a separate session.fork({sessionID, boundary}). Note a beta codegen conflict: the standalone SessionForkBoundary alias declares messageID on both before and through variants, but the SessionForkInput actually accepted by client.session.fork declares through as {type: "through"} with no messageID — treat the fork input contract as unresolved (§5).
  • SessionInfo is richer: parentID/fork lineage, location, active agent/model, cumulative cost: MoneyUSD and tokens: TokenUsageInfo, outcome?: "succeeded"|"failed"|"interrupted", revert state.
  • New session surface: import/export, compact, revert.stage/clear/commit, inbox.{list,cancel,steer,queue}, instructions.entry.{list,put,remove} (keyed instruction store), environment, background, view, log({after?, follow?}) (replayable durable event log), stats, active, synthetic, shell, skill, generate({sessionID, prompt}) → {text}.
  • credential.{update,activate,remove} replaces v1 auth.*; integration.* replaces provider-auth helpers.

1.5 Messages and content

  • SessionMessageAssistant is self-contained: {content: Array<Text|Reasoning|Tool>, agent, model: ModelRef, finish?: "stop"|"length"|"tool-calls"|"content-filter"|"error"|"unknown", rawFinish?, cost?, tokens?, error?: SessionStructuredError, retry?, snapshot?}. v1's parallel {info, parts[]} shape is gone; there are no step-start/step-finish parts (step lifecycle is events), and no synthetic/ignored flags on assistant text.
  • Tool content: {type: "tool", id, name, executed?, state, …} (v1: callID/tool). States are streaming {input: string} → running {input: JSON object} → completed {input, content: [ToolContent, …]} | error {input, error, content?} — no pending state (only the streaming state carries a string input; the later states carry a JSON object), and results are a content array ({type:"text"} | {type:"file", uri, mime, name?}), not a string output + attachments. Tool file references use uri, not url. The v1 running state's title (which the provider forwards as tool-input-start.title) has no typed v2 equivalent — drop it deliberately or enrich only from guarded metadata.
  • Direct assistant file outputs are removed. v1 assistant messages could carry top-level file parts, which the provider maps to AI SDK file/source content in both generation modes independently of tool attachments. v2 assistant content permits only text, reasoning, and tool entries — files surface only inside tool-result content; SessionStepEnded.files/snapshot are bare path strings with no MIME/content contract and are not an equivalent. This is a removed capability the migration must document (with a warning), not a mapping change.
  • session.context returns a broad message union (agent-selected, model-selected, location-switched, user, synthetic, system, skill, shell, assistant, compaction) — consumers must filter deliberately.
  • Message history reads move to message.list (not session.messages).

1.6 Events (streaming)

  • client.event.subscribe(requestOptions?) → AsyncIterable<V2Event> — no awaited {stream} wrapper, no directory/session filter argument; filtering is client-side. The session ID does not live at one uniform path: most session events carry data.sessionID, but form.created carries it at data.form.sessionID — a naive data.sessionID filter silently drops form requests and can deadlock generation. Session extraction must be discriminated by event type.
  • Near-uniform envelope {id, type, location?, durable?: {aggregateID, seq, version}, data} with created on all but server.connected (V2EventServerConnected lacks it) — the provider's dual properties/data tolerance becomes single-shape, but don't assume every envelope field on every member.
  • Delta-native streaming: session.text.started/delta/ended, session.reasoning.started/delta/ended (text and reasoning are both keyed by {assistantMessageID, ordinal}, so reducer identity must include the content kind — e.g. ${assistantMessageID}:text:${ordinal} vs :reasoning:), session.tool.input.started/delta/ended (keyed by tool id; started carries name), session.tool.called/success/failed (these three carry an executed flag; session.tool.progress does not), session.step.started/ended/failed (ended carries finish, rawFinish, cost, tokens, snapshot), session.execution.started/succeeded/failed/interrupted (interrupted.reason: "user"|"shutdown"|"superseded"), session.retry.scheduled, session.usage.updated, inbox events, permission.asked/replied, form.created/replied/cancelled, plus non-session noise (TUI, MCP, filesystem, catalog). (session.usage.recorded is not in the live union — see the durable split below.)
  • Correlation gap: the prompt receipt and inbox events expose an inbox ID; execution lifecycle events expose only sessionID; step events add assistantMessageID but no inbox ID. On a shared/existing session, an event pump can therefore attribute another client's execution (e.g. the TUI's) to this call — and a provider-local lock cannot exclude external clients. Until upstream documents an inbox→execution correlation key, deterministic lifecycle handling is only achievable on sessions this provider creates and exclusively owns (one conversation, one session, one active generation — note the session must still survive across a tool-approval round-trip, so "ephemeral" is per-conversation, not per-HTTP-call), and shared-session mode must carry an explicit exclusivity caveat.
  • Durable vs transient — two different unions, not a subset: session.log yields SessionLogItem = SessionEventDurable | EventLogSynced (a log.synced sentinel the reader must handle). The durable union includes lifecycle/terminal events but not text/reasoning/tool-input deltas, and the two unions genuinely diverge: SessionUsageUpdated is live-only while SessionUsageRecorded is durable-only. A recovery design that "replays V2Events from the log" is therefore type-incorrect — the reducer needs an explicit normalization layer over both unions. After an SSE drop, lifecycle state is recoverable but live deltas are not; final-message reconciliation is required. Crucially, PermissionAsked/Replied and Form* events are also absent from the durable union, and a session blocked on one may remain without a terminal execution event while the request is pending — so reconnect recovery must additionally poll permission.list/get and form.list/form.state (deduplicating against already-handled request/form IDs), not just replay the log.
  • Note SessionStepFailed is not error-only: it can carry finish?: "content-filter", rawFinish, cost, and tokens — a reducer that reads usage/finish only from SessionStepEnded loses failed-step accounting and the content-filter reason.

1.7 Questions → Forms

No question.* API exists. Replacement: form.request.list, form.list/create/get/state/reply/cancel; FormInfo {id, sessionID, title, metadata?, fields} with typed fields (string w/ options+format, number, integer, boolean, multiselect w/ min/max, external {url}), per-field key, conditional when clauses, defaults. form.reply takes answer: Record<key, string|number|boolean|string[]> — keyed, not v1's positional string[][]. form.cancel replaces question.reject. Errors: FormNotFoundError, FormAlreadySettledError, FormInvalidAnswerError. form.state enables a polling fallback when SSE is unavailable.

1.8 Permissions

  • permission.asked data: {id, sessionID, action, resources[], save?, metadata?, source?: {type: "tool", messageID, id}, message?} — v1's permission→action, patterns→resources, tool.callID→source.id.
  • permission.reply({sessionID, requestID, reply: "once"|"always"|"reject", message?}) — sessionID newly required; no directory.
  • Per-session rulesets at create are gone; v2 rules live on agents (AgentInfo.permissions) and project-persisted saved permissions (permission.saved.list/remove). permission.create creates/evaluates a live request — it is not a policy-installation API. In embedded mode, the plugin permission.hook("evaluate") can programmatically allow/ask/deny (docs).

1.9 Finish, usage, cost, structured errors

  • finish is a closed union aligned with AI SDK ("unknown" → other is the only normalization), plus native rawFinish. Available per-step (SessionStepEnded, and SessionStepFailed for "content-filter") and per-message.
  • TokenUsageInfo {input, output, reasoning, cache: {read, write}} maps directly onto the provider's StreamingUsage accumulator (inputTokens/outputTokens/reasoningTokens/cachedInputTokens/cachedWriteTokens, minus totalCost); MoneyUSD cost appears separately on steps, messages, and sessions.
  • v1's named error classes (MessageAbortedError, MessageOutputLengthError, ContextOverflowError, StructuredOutputError, ProviderAuthError, …) are replaced by SessionStructuredError {type: string, message, status?} on execution/step/tool failures and retry records. All error.name-based mapping breaks.

1.10 Structured output: removed

No format/json_schema parameter exists anywhere in the v2 beta prompt path, and there is no StructuredOutput tool (grep of the full types: format appears only as a form-field format and a config formatter). generate.text({prompt, model?}) and session.generate({sessionID, prompt}) return {text} only. The docs explicitly describe generate.text as generating "without creating a session, invoking tools, or adding to session history"; session.generate is described only as a transient generation request — do not assume it is tool-free until verified. This is the provider's biggest user-facing regression: responseFormat: {type: "json"} (and therefore Output.object()/generateObject-style flows) has no server-side enforcement to target.

1.11 Service management

createOpencodeServer is gone. @opencode-ai/client/service: Service.discover({file?, version?}), Service.ensure({file?, version?, command? (default ["opencode","serve","--service"]), env?, onStart?(reason: "missing"|"version-mismatch", prev?)}) → Endpoint {url, auth?}, Service.stop({file?}), Service.headers(endpoint). Discovery is via an XDG-state registration file with version predicates — not port probing. There is no hostname/port/timeout knob; the service is a shared, registered process, not a child the provider owns. client.health.get() → {healthy, version, pid} and client.server.get() replace raw health probes. client.migration.v1.status() reports v1→v2 data-migration state (required/running/completed/error) — a useful connection preflight.

2.2 File-by-file

package.json — swap dep to @opencode-ai/client (exact pin while beta; no caret). Embedded @opencode-ai/sdk as optional peer behind a ./embedded export with dynamic import — never in the default graph (Effect RC + six sibling packages). Keep Node >=22, ESM-only. This is semver-major (5.0.0).

src/types.ts — retype OpencodeClient from @opencode-ai/client (ReturnType<typeof OpenCode.make>); collapse clientOptions to {fetch?, headers?}. Remove/deprecate: systemPrompt, tools, permission (create-time), outputFormatRetryCount, cwd, onQuestion/questionPolicy. Add: location {directory, workspaceID?} (settings.directory maps to location.directory), delivery, resume, onForm/formPolicy (default formPolicy: "cancel" — the non-deadlocking analog of today's questionPolicy: "reject" default), session mode (ephemeral/persistent/existing), service options, file-URI resolver hook. providerOptions.opencode.messageID → prompt id (drop the msg_ prefix assertion pending upstream confirmation). Expand OpencodeProviderMetadata: tokens, finish/rawFinish, inboxId, outcome, structured error, retry info.

Session-setting migration map (v4 → v5):

v4 setting/API v5 disposition
sessionId Kept: pins an existing v2 session (with the shared-session exclusivity caveat, §1.6); validate with session.get + migration.v1.status preflight, and decide whether a mismatched location rejects or triggers session.move
createNewSession Semantics change — document as a break. Today true creates a fresh session on every generation call (bypassing the cached/preset session). Pure per-call isolation is incompatible with v2's tool-approval continuation, which must reattach to the blocked session across calls. src/opencode-client-manager.ts — near-total rewrite. Delete: dynamic @opencode-ai/sdk/v2 imports, createOpencodeServer + server.close(), unauthenticated /health→/config probes, responseStyle/directory client options, hostname/port/timeout plumbing, and the process-exit/SIGINT/SIGTERM/uncaughtException handler suite (a library should not own process termination, and a shared service must not die with one consumer). Replace with explicit backends: (1) caller-supplied client; (2) caller-supplied manager (the current clientManager injection setting — retain it, retyped to the new manager interface, or explicitly document its removal as a v5 break); (3) baseUrl → OpenCode.make (+ user headers); (4) connect-without-start (the current autoStartServer: false mode) → Service.discover() and fail clearly when no registered service exists — hostname/port probing has no v2 equivalent, so this public mode must be re-based on discovery (or on an explicit baseUrl), not silently deleted; (5) auto-start → Service.ensure({version: predicate, onStart}) + OpenCode.make({baseUrl: endpoint.url, headers: merge(Service.headers(endpoint), userHeaders)}); (6) embedded host (optional entrypoint). Disposition the small public manager API alongside: createClientManager/createClientManagerFromSettings re-typed to the new backends, getServerUrl() → endpoint URL for baseUrl/service backends, the configured URL if known for caller-supplied clients, and undefined (or a typed error) for the embedded host, which exposes no endpoint; isServerManaged() → "started by this provider" (meaningful only in owned-service/embedded modes); any manager cache/registry must key on the full effective identity (baseUrl or registration file, headers/auth, custom fetch), not just host/port. Disposal never stops a shared service (see §2.1 ownership row); an "owned service" mode requires a provider-controlled registration file. Preflight migration.v1.status() and health.get() version gating. Ownership and headers must be explicit per backend: dispose closes an owned embedded host and aborts this provider's subscriptions, but never closes caller-supplied clients/managers or the shared service; per-call AI SDK headers must reach every request in a generation (subscribe, prompt, wait/read, form/permission replies, interrupt), merged over client-level and Service.headers values — filtering out undefined entries first, since LanguageModelV4CallOptions.headers permits them and the RequestInit record form does not. Keep SSE-abort registration (subscribe returns an AsyncIterable; verify loop-exit cancels the response body). Avoid the mutable singleton pattern — key managers by endpoint/backend.

src/opencode-language-model.ts — the central rewrite.

  • Session establishment: session.create({title, agent, model: {id, providerID, variant?}, location}). Bare model IDs need a decision: the current provider accepts "modelID" without a provider prefix (parsed with empty providerID, and the model field is simply omitted from the v1 prompt so the server default applies); v2 ModelRef requires both id and providerID, but SessionCreateInput.model is optional — so the equivalent behavior is to omit model at create (server/session default), optionally resolving bare IDs via model.default()/the catalog; document whichever is chosen. One wrinkle: a bare model ID combined with settings.variant cannot omit the model (variant rides ModelRef), so that combination must resolve a providerID via the catalog or be rejected. Treat model/agent as immutable per model instance; a different model on a reused session ⇒ switch-then-prompt must be serialized, or prefer session-per-model. Default to one active generation per exclusively-owned session — note a provider-local lock cannot exclude external clients (TUI) on shared sessions; see the correlation gap in §1.6. And because LanguageModelV4 calls carry no conversation identifier while the session must persist across approval round-trips, the session↔conversation binding needs an explicit rule: one model instance = one conversation = one pinned session (documented constraint, matching the current provider's single mutable sessionId), with providerOptions.opencode.sessionId as the per-call escape hatch for callers managing sessions themselves.
  • doGenerate: subscribe to events before prompting, and establish readiness before the prompt goes out — starting iterator.next() alone doesn't prove the server registered the stream; treat the initial server.connected event as the readiness handshake (verify it is emitted on subscribe, else fall back to a bounded readiness race). Reply approvals via the new permission.reply shape; session.prompt(...) → keep the receipt; complete via execution events with session.wait as watchdog; fetch the assistant message (message.list/session.message keyed by SessionStepStarted.assistantMessageID); map content[], finish/rawFinish, tokens, cost (consuming SessionStepFailed's finish/usage as well as SessionStepEnded's). Forms/permissions must be handled concurrently or the wait deadlocks. Handle SessionBusyError (retry with delivery: "queue" or surface clearly).
  • doStream: one event pump; extract the session ID per event type (data.sessionID for most, data.form.sessionID for form.created); map deltas 1:1; finish on session.execution.succeeded/failed/interrupted (never on an intermediate step's "tool-calls" finish; keep session.idle only as a hang-prevention backstop). On execution.failed, prefer the failing step's own SessionStepFailed.finish ("content-filter") and its cost/tokens when present over a generic error — the execution-failed event itself carries only the structured error. Map all three interruption reasons: "user" → finish stop (raw "interrupted:user"); "superseded" → finish other (another inbox item steered over this turn — surface in provider metadata); "shutdown" → finish error (server went away mid-turn); mark these provisional pending upstream docs. Abort → cancel the pending inbox item if undelivered, else session.interrupt({continue: false}); emit raw events under includeRawChunks.
  • Approvals (two-phase round-trip — a design the current draft of the code has no v2 answer for): AI SDK approval responses arrive in a subsequent doGenerate/doStream call, and that call must not issue a new session.prompt — v2 requires text on every prompt, and a new prompt would enqueue a second user message on top of the still-blocked execution (duplicate work or deadlock). Phase 1: surface tool-approval-request (correlate via PermissionAsked.data.source.id; source is optional, so source-less requests fall back to the request id with no tool correlation, as today) and finish the call; the session must therefore be pinned across the approval boundary (the model instance's session state / providerMetadata.opencode.sessionId), which is why "ephemeral" means session-per-conversation, not session-per-HTTP-call. Phase 2: detect an approval-only prompt (approval responses, no new user content) → subscribe and complete the readiness handshake first → then permission.reply({sessionID, requestID, reply}) → observe the original execution to completion (events + wait, reconciling via durable log / polls / final message) → return its result. Ordering matters: the reply can resume the blocked execution instantly, so deltas, a further approval/form, or completion can fire before a late subscriber is listening — the same subscribe-before-trigger rule as the prompt path. Preserve the issue-#22 ordering machinery (buffer approval until tool-input-available) with the new keys.
  • Forms: port the question dedup/in-flight/retryable machinery keyed by form id; reply keyed answers; form.cancel on policy/handler failure.
  • Content extraction: map content[]; tool results serialize the ToolContent array as structured JSON + emit file URIs as separate file/source parts (keep the raw array in provider metadata); delete all StructuredOutput flattening.

src/convert-to-opencode-messages.ts — output becomes {text, files[], warnings} (+ separated system block for the embedded path). Transcript serializer with stable delimiters/escaping; reused-session mode sends only the latest user turn; file parts go through the URI resolver or warn.

src/convert-from-opencode-events.ts — rewrite against the generated V2Event union (~70% deletion): drop getEventPayload, snapshot diffing, lastTextContent/lastReasoningContent, messageRoles, reasoning-vs-text partID guessing, synthetic/ignored filtering, question branch, STRUCTURED_OUTPUT_TOOL. Reducer keyed by {sessionID, assistantMessageID, ordinal|toolId}; stable AI SDK block ids like ${assistantMessageID}:text:${ordinal} (kind included — text and reasoning share the ordinal keyspace); capture tool name from input.started (later events don't repeat it); tolerate duplicate durable events. The reducer's input layer must normalize the two distinct unions — live V2Event vs session.log's SessionLogItem (durable events + the log.synced sentinel) — rather than assuming log replay yields V2Events.

src/map-opencode-finish-reason.ts — shrinks to a table: five values map 1:1, "unknown"→other, raw = rawFinish ?? finish; interrupted-by-user → stop; delete the error-name switch and resolveStructuredOutputFinishReason.

src/errors.ts — rebase on _tag guards + a total ClientError.reason mapping (all five reasons): "Transport" → phase-aware retryability: the AI SDK auto-retries the entire call when APICallError.isRetryable is set, so only provably pre-dispatch failures (subscribe, session.create, anything before the prompt/permission-reply was sent) may be marked retryable; a transport failure after dispatch — or with uncertain delivery — must be non-retryable and reconciled through the pinned session's wait/log/message state instead, or the retry itself enqueues duplicate work; "UnexpectedStatus" → non-retryable APICallError by default, with no status promise: the public ClientError type exposes only reason and an untyped cause, so a status code (for 429/5xx retry classification) is recoverable only via guarded runtime inspection of the cause or a custom-fetch side channel — treat as unknown-status when absent; "UnsupportedContentType" and "MalformedResponse" → non-retryable protocol errors (server/client contract mismatch — surface a version-skew hint); "SseEventTooLarge" → non-retryable without a different transport strategy. Tagged errors: UnauthorizedError/ForbiddenError → auth errors; SessionBusyError/ConflictError → conditionally retryable with backoff; validation/not-found/form-invalid → non-retryable; ServiceUnavailableError → retryable pre-dispatch only. The phase rule is universal, not Transport-specific: no error of any kind may surface as a retryable APICallError once the prompt (or a permission reply) has been dispatched — e.g. a 503 thrown by the post-prompt session.wait watchdog must be retried internally against the pinned session (re-wait/log/message reconciliation), because a retryable surface error makes the AI SDK rerun the whole call and submit a duplicate prompt. Add a second normalization path for SessionStructuredError from events. Never auto-replay a tool-capable execution after transport failure (it may already have mutated the workspace).

src/validation.ts / logger.ts / opencode-part-utils.ts / opencode-provider.ts / index.ts — schema updates for removed/added settings; part-utils gains a URI branch and loses v1 attachment planning; provider factory splits by backend; index re-exports form/permission/v2 event types and drops question/envelope-era exports. logUnsupportedCallOptions remains correct — v2 still has no sampling parameters on the prompt path.

Tests, examples, README — every mock encodes the v1 protocol ({info, parts} prompts, {stream} subscriptions, question.*, session.abort, responseStyle, createOpencodeServer): full rewrite around receipts + event fixtures + typed errors. Examples: question-handling → forms; generate/stream-object → explicitly degraded prompt-mode JSON; abort → interrupt; client-options → headers/fetch/Service. README must stop claiming native json_schema, per-request system/tools, and v1 attachment behavior.

3. Improvement opportunities (what v2 makes better)

  1. Delta-native streaming. 1:1 mapping to AI SDK text/reasoning/tool-input start/delta/end parts; kills prefix-slicing, snapshot/delta divergence bugs, the reasoning-vs-text disambiguation hack, and re-stringified tool input. Several hundred lines and a whole bug class deleted; tool-input streaming becomes genuinely incremental string deltas instead of re-diffed snapshots.
  2. Typed events imported from the package. Deletes ~300 lines of hand-rolled event/part interfaces and the dual-envelope shim; compile-time drift detection against future betas.
  3. Typed thrown errors. Deletes extractSdkResult and both error-shape paths; honest retry classification from _tag/reason instead of string sniffing; structured fields (sessionID, providerID, field) flow into error metadata. Ends the "silent fields-style failure" class the 3.0.5/4.0.0 releases patched.
  4. Standardized finish + native usage/cost. Table-lookup finish mapping with native rawFinish; per-step tokens/cost from SessionStepEnded and SessionStepFailed plus message/session totals — no part archaeology. (Open question: whether step tokens are incremental or cumulative — verify before summing.)
  5. Explicit turn lifecycle. execution.succeeded/failed/interrupted distinguishes a turn ending from the session being idle — a far better completion signal than v1's idle inference; session.wait simplifies the non-streaming path (with the forms/permissions caveat). Caveat: lifecycle events carry no inbox ID, so this is only deterministic for this call's turn on a session the provider exclusively owns (§1.6 correlation gap).
  6. Service.ensure + typed health. Version-predicate gating, shared daemon across tools, basic-auth handling, onStart observability; deletes the most accident-prone parts of the client manager. migration.v1.status gives actionable preflight diagnostics.
  7. Embedded host mode (flagship opportunity). OpenCode.create() is call-site compatible with the network client — a ./embedded entrypoint gives zero-server, zero-port, zero-auth operation, and is also the best integration-test harness (real OpenCode in-process instead of mocks). Plugins recover what the network path lost: true system-prompt injection (ctx.agent.transform / ctx.session.hook("context") pushing onto event.system), per-session tool filtering (ctx.session.hook("context") mutating event.tools), programmatic permission policy (ctx.permission.hook("evaluate") — noting an explicitly configured deny is final and bypasses the hook), custom tools (ctx.tool.transform's add()). Workerd opens a Durable Object deployment path later.
  8. Inbox delivery semantics. Expose delivery: "queue" and "steer" plus resume — a real concurrency/steering story the provider never had. (Recommend queue as the provider default to avoid SessionBusyError, pending verification of the server's actual default and steer/resume behavior — §5.)
  9. Session fork / import / durable log. Fork for branching and side-effect-free retry loops (note the fork-input codegen conflict, §1.4); session.import as the candidate for structured history seeding on fresh sessions (verify accepted shapes — session.synthetic is text-only); session.log({after, follow}) for SSE-drop recovery with sequence numbers (transient deltas still require final-message reconciliation).
  10. Headers + includeRawChunks. Forward AI SDK per-call headers (auth/tracing/tenancy); emit raw typed events for advanced consumers — both currently ignored options.
  11. Richer approvals/forms metadata. action/resources/save and source.{messageID, id} correlation beat v1's permission/patterns; typed form fields beat positional string arrays; form.state polling is a resilience fallback.
  12. generate.text / session.generate. Cheap side-calls (titles, JSON repair attempts, policy checks): generate.text is documented as no-session/no-tools/no-history; session.generate is documented only as transient (tool behavior unverified). Never a silent substitute for the main model invocation.

4. Strategy and sequencing

Clean-break major, not dual-runtime support (unanimous): the contract differs at every layer; a runtime v1/v2 switch would double every code path and the 8,000+-line test surface for a v1 line OpenCode itself is replacing.

ai-sdk-provider-opencode-sdk 4.x   → OpenCode 1.18.x servers, maintenance only
ai-sdk-provider-opencode-sdk 5.x   → OpenCode v2, dist-tag "next" until upstream stabilizes
  "."          network client (@opencode-ai/client only)
  "./embedded" optional in-process host (@opencode-ai/sdk as optional peer, dynamic import)
  (evaluate "./service" re-exports and "./workerd" after demand/runtime validation)

Sequencing:

  1. Now: spike branch against an exact-pinned beta; file upstream issues for the four hardest gaps (structured output, per-prompt system, file-URI ingestion semantics, inbox→execution correlation) while the API is still movable. Optionally add a 4.x warning when the connected server looks like v2: the manager's current raw /health//config fetches are availability checks only, and the typed per-instance health response (V2HealthGetResponse) carries no version — but the v1 SDK's global health response (GlobalHealthResponse) includes version: string; use that, with the v2-only route GET /api/experimental/migration/v1 (the generated migration client's actual path) as a fallback signal.
  2. Core first: narrow internal client-port interface (only the methods the model needs — makes both network and embedded backends structurally satisfy it, and isolates beta churn in one facade); event reducer against recorded fixtures; then doGenerate/doStream on receipts + lifecycle events; network mode with caller-supplied client/baseUrl.
  3. Then: Service.ensure path (auth, version predicates, non-owning disposal, migration preflight).
  4. Then: embedded entrypoint + plugin-restored features (system injection, tool filtering, permission hooks) as experimental.
  5. GA (5.0.0 on latest) only after OpenCode v2 ships a stable client and one soak cycle of integration tests passes; keep the beta line on next until then.

Testing: contract tests pinned to the exact beta (fail CI on generated-API drift); pure event-fixture tests for the reducer (delta interleavings, approval-before-tool-call ordering, duplicate durable events, step-vs-execution failure, retry scheduling); typed-error mapping per _tag; integration tests gated on an available v2 binary (prompt→wait→read, forms during wait, interrupt mid-stream, SessionBusyError/queue, auth headers, file URIs); embedded-host in-process integration tests; packed-artifact tests (root import must not resolve Effect; entrypoint isolation); differential v1-vs-v2 provider runs comparing AI-SDK-level outputs.

5. Open questions (genuinely unresolved by beta types/docs)

Prompt/execution semantics

  1. How is a SessionInboxUser.id correlated to an execution and its assistant message(s)? (SessionStepStarted.assistantMessageID exists, but no shared inbox key.)
  2. What exactly does session.wait wait for (current execution? all queued items? background compaction/title jobs?), and does it reject or resolve on execution failure — or hang on a pending form/permission?
  3. Default delivery when omitted; precise resume semantics (after interrupt? after failure?) and interrupt({continue: true}) meaning; what triggers interrupted.reason: "superseded".
  4. Can one session run concurrent executions, or is it always serialized (determining whether provider-level locking is correctness or caution)?
  5. Prompt id constraints (v1 required msg_ prefix) and idempotency on retry.

Files 6. Which URI schemes does files[].uri accept — data:, file:, workspace-relative, http(s)? Who fetches remote URIs, under what credentials (SSRF surface)? Is an upload API planned?

Content/usage 7. Are SessionStepEnded.tokens incremental per step or cumulative? Does output include reasoning tokens, and does input include or exclude cache.read/cache.write? (The type alone doesn't prove it, and it blocks safe derivation of the AI SDK total/noCache/text fields — the provider currently assumes input excludes cache and sums them for the total.) 8. Can one execution produce multiple assistant messages, and what event-ordering guarantees exist (tool-input-start before permission.asked? content-ended before execution.succeeded?) 9. Tool executed flag semantics at each lifecycle point (maps to AI SDK providerExecuted?); should mixed text/file tool content preserve ordering? 10. Authoritative rawFinish when step and message values differ.

System prompt / permissions / forms 11. Is session.instructions.entry.put a real system-prompt vehicle (does it enter model context; does it survive compaction), or what is the intended per-session system story? 12. How are permission rules installed programmatically in network mode (no create-time field; permission.create looks evaluation-flavored; is permission.saved the replacement)? 13. Does execution block on pending forms (almost certainly — confirm, since session.wait would then deadlock without a handler), and can multiple forms be pending at once? How should external form fields be handled by a generic callback? Does form.cancel fail the tool, the turn, or continue? 14. The v2 sdk's contracts still re-exports a Question schema — dead code or a sign questions may return? (Watch before investing heavily in forms.)

Events/service/runtime 15. Does event.subscribe support server-side filtering or replay/cursors (or is session.log the only catch-up), and is the stream location-scoped or server-global? 16. Service.ensure version predicate against 0.0.0-beta-N builds; basic-auth username convention; concurrent ensure/stop against one registration file; is an ensured service intended to be shared/persistent (ownership/lease model)? 17. Official runtime matrix (no engines anywhere; docs use bun): Node floor for /service, embedded-host Bun support, workerd maturity (production-intended? events across DO eviction?). 18. Does a required v1 migration block v2 session APIs, and is there a programmatic migration trigger beyond status? 19. Does the Promise client intentionally discard response headers (needed for AI SDK response metadata)? 20. Is structured output intentionally removed or not yet implemented — and is @opencode-ai/sdk v1 getting a compat window after v2 GA (timeline to stable)? 21. Is the SessionForkInput/SessionForkBoundary mismatch (the callable input's through variant lacks messageID while the standalone alias includes it) a codegen bug or intentional shorthand? 22. session.import's shape is typed (SessionTransferData {info, messages: SessionMessageInfo[]}) — the unresolved question is whether arbitrary constructed transfers (synthesized from AI SDK history rather than exported from a real session) are accepted and sanitized, or whether import only round-trips genuine exports.
